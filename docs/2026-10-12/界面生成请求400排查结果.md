# 界面生成请求 400 排查结果

## Intent：最终目标

消除当前前端与本地 AI 服务请求契约不一致造成的 HTTP 400。

## Data：证据与执行细节

### 根因

实际运行的旧生成服务只接受主题 `minimal`、`technical`、`warm`，而当前客户端使用 `natural`、`electronic`、`dark`。请求在 `workflowRequest.safeParse()` 阶段被拒绝，尚未进入模型生成。旧字段契约也不支持当前客户端可能发送的 `choices`。

网关 `services/gateway/src/interface-workflow.ts` 会将生成服务的 HTTP 400 改写为 `INTERFACE_AI_GENERATION_FAILED`，与用户提供的错误响应一致。这导致错误名称看起来像模型生成失败，实际是运行版本未同步。

### 处理

源码已包含新契约，无需修改客户端或服务端业务代码。在相邻 `aily-blinker-services` 仓库执行：

```sh
docker compose -f compose.dev.yaml build gateway device-ui-agent

docker compose -f compose.dev.yaml up -d --no-deps --wait --wait-timeout 60 gateway device-ui-agent
```

构建前检查 Compose 解析结果，确认网关 HTTP 对外端口仍是 17000。仅更新 Gateway 和生成服务两个容器，沿用数据卷和现有配置。

### 验证

- Docker 镜像构建成功，包含 Gateway TypeScript 构建和生成服务严格类型检查、Rslib 构建。
- 两个更新后的容器均为 healthy；数据库、Redis、Broker 和 Controller 仍保持原有运行实例。
- `http://127.0.0.1:17000/healthz` 返回 HTTP 200。
- 从更新后运行容器重新读取编译产物，AST 检查确认主题已为 `natural`、`electronic`、`dark`，字段 schema 已支持 `choices`。

## Edges：边界与限制

- 未新增测试，未使用浏览器 UI，未读取或输出用户登录令牌和模型密钥。
- 未修改请求校验规则，没有去掉 strict 校验或将新主题伪装成旧主题。
- 未提交真实用户的完整生成请求，未验证后续模型生成、预览上传和视觉审查全部完成。
- 本次修复运行版本不一致；网关将参数错误泛化为生成失败的诊断问题仍保持原样，未扩大修改范围。

## Answer：交付与后续使用

导致本次 400 的旧运行契约已替换为当前源码契约。用户可在现有界面配置页再次点击 AI 生成。运行环境无需再次启动，网关地址仍为 `http://127.0.0.1:17000`。

架构图和数据流图见同目录《界面生成请求400排查计划》。

## 自我复核

此次结论基于实际运行产物与客户端请求构造的对比，不能仅凭源码最新就断言服务已更新。修复采取重建本地服务，不引入兼容补丁、请求硬编码或额外重试。服务健康与新契约生效已经确认，但不将其等同于真实模型生成链路已全部验收。
