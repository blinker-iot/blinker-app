# 设备列表恢复排查结果

## Intent：最终目标

恢复此前本地开发所使用的网关环境，检查真实设备记录是否仍在，并区分数据存在、服务可达和浏览器恢复显示三个验证层次。

## Data：可用证据

- `npm start` 对应 development 环境，连接 `https://iot.yiyu.pro`。前两次启动都未指定 local 配置；只改前端 host 没有修正网关。
- 10 月 10 日的项目记录使用本地 Gateway `http://127.0.0.1:17000` 和 local 构建。
- 在 PostgreSQL 的只读事务中查询 `v2_logical_devices`：共 1 条设备记录，名称 `test`，类型 `diy`，状态 `active`，`deleted_at` 为空。
- 设备目录缓存键包含网关地址和账号；即使前端访问来源相同，更换网关也不会读取原网关对应的目录缓存。
- `UserService.getAllInfo()` 从当前网关获取账号、自有设备、接收的分享设备。目录 API 失败时写入 `deviceLoadError`；首页目前仅根据设备数显示空状态，没有呈现该错误。

## Edges：边界与限制

- 仅停止本聊天启动的前端服务并以正确参数重启；未修改应用业务代码、默认环境配置、数据库或浏览器存储。
- 未访问浏览器，未读取认证令牌，未进行用户账号的认证设备列表请求。
- 数据库中的 `active` 是设备记录状态，不代表设备当前在线。
- 本地记录仍在不能证明它属于当前浏览器会话，也不能证明用户提到的所有设备都仍在；目前明确核实的是 `test` 这一条记录。
- 未新增测试。没有扩大修改到首页错误提示或会话存储机制。

## Answer：交付与验证

当前开发服务使用以下命令运行：

```sh
npm start -- --configuration local --host 127.0.0.1
```

- 设备模板和 Angular 编译均成功。
- `http://127.0.0.1:4200/` 返回 HTTP 200。
- 对实际服务提供的入口及静态依赖执行 AST 检查，共检查 23 个模块，确认唯一的 `gatewayBaseUrl` 为 `http://127.0.0.1:17000`。
- 本地 `/api/v2/devices` 的未认证请求返回 HTTP 401，证明接口可达且要求登录；此结果不代表已验证账号设备列表。
- 用户需要刷新原来的 `127.0.0.1:4200` 标签页；若会话失效，使用之前添加设备的同一账号登录。开发 Web 会话保存在 `sessionStorage`，重新打开标签页可能需要登录。
- 排查计划及 Mermaid 架构图、数据流图见同目录《设备列表恢复排查计划》。

## 自我复核

初次处理只关注 `localhost` 与 `127.0.0.1` 的来源隔离，证据不足以解释真实设备列表缺失。此次进一步确认了前端访问来源、构建配置、后端数据环境三个独立维度，并修正启动环境。已确认本地设备记录存在和实际前端产物连接本地网关；尚未宣称浏览器中的设备列表恢复，最终显示仍需用户刷新后确认。
