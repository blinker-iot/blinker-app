# 邀请链接权限开关执行记录

## Intent：最终目标

为已有邀请链接提供控制设备、编辑控制台两个 switch，并收紧公开链接卡片的顶部留白。

## Data：完成的修改

### 邀请权限

- 弹窗使用现有开关样式，分别修改控制设备和编辑控制台；每次只 PATCH 当前变更的字段。
- 保存期间禁用重复切换及复制。成功后同步弹窗与列表，失败后重新读取服务端权限；读取失败则关闭详情。
- 页面离开、账号切换、弹窗关闭均有回包隔离，不重新打开旧详情。
- 后端现有邀请资源增加 PATCH，只允许 `role`、`canEditConsole`，至少传一个。
- GET 与 PATCH 复用待接受链接的检查，按邀请记录、设备的顺序加锁，与接受流程一致。
- 只允许当前设备所有者修改未过期的 pending 链接邀请，不修改已生成的成员授权。
- 保持 operator 时保留原端点范围；关闭控制后按 viewer 规范清空端点范围。再次明确开启控制按现有 operator 默认语义处理。
- 增权时检查设备路由，缩权不依赖路由正常。同状态保存直接返回。
- SQL 只更新权限与更新时间，不修改创建摘要、幂等键、token、邀请 ID 和有效期。

### 卡片间距

- 公开链接卡片顶部 padding 从 10px 调为 4px，底部从 14px 调为 12px。
- 根据后续截图反馈，将标题行下方间距从 4px 调为 0，复制按钮行高从 36px 调为 32px，进一步收紧标题与地址间距。
- 邀请弹窗的有效期、控制设备、编辑控制台合并为同一淡色设置区，统一 52px 最小行高、13px 标签字号与分隔线；设备名称独立置于上方，减轻字重。

### 核对

- App local 构建与 Gateway 构建通过。
- 3 个相关已有前端文件、33 项检查通过。
- 在现有待接受邀请的临时事务中调用权限更新，确认两个开关分别生效，另一权限和受控端点范围不被意外覆盖，原 code、到期时间、创建摘要和 token hash 不变；事务已回滚，用户当前权限没有被验证操作改变。
- 后端 6 个已有文件共 38 项检查通过：首次运行 37 项通过，1 项 E2E 在设备分配阶段受运行容器环境影响失败；仅为该测试进程设置 `BROKER_ALLOCATION_RECONCILER_ENABLED=false` 后重跑通过。
- E2E 预期使用默认静态分片分配，但继承了容器的真实 allocator 开关；未修改业务代码、运行服务配置或测试用例。
- 前后端只读复核未发现阻断问题。
- 本机 Gateway 已重新构建并启动，容器 healthy；App 4200 与 Gateway 17000 健康端点均返回 HTTP 200。

## Edges：边界与限制

- 没有新增测试用例，没有使用浏览器进行 UI 确认。
- 链接权限只影响尚未接受的邀请；接受后仍从成员权限入口修改。
- 当前 App 创建的链接不限制控制字段。将来若开放字段范围选择，需要同时设计关闭再开启控制时的范围恢复交互，不能靠隐藏历史字段自动恢复权限。
- 未增加数据库迁移、邮件发送或远端部署。
- 本次统一 GET/PATCH 与接受邀请的锁序；旧有其他流程仍保留原锁序和事务重试，不声称消除全部潜在死锁。

## Answer：交付与成功标准

- 已有邀请弹窗支持两个权限开关，切换自动保存，并保留查看与复制链接功能。
- 公开链接卡片顶部留白缩小。
- 文档遵循 IDEA；架构图与数据流图见《邀请链接权限开关计划》。

## 自我批判

- 不能通过重新创建邀请实现权限修改，否则链接、有效期和幂等语义都会变化；本次直接更新原邀请。
- 不能把省略控制字段范围解释为全部控制；本次在事务内保留原 operator 范围。
- 前端不能只依赖乐观状态宣称保存成功；失败后以重新读取的服务端状态为准。
- 构建通过只能证明模板和代码可编译，间距效果未经过浏览器视觉确认。
