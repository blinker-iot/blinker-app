# 最小自动化产品收口执行方案

更新：2026-10-11。M1～M5及N1～N5各自限定本机范围收口；N5匹配新版App/Gateway/Broker与两设备uint32 50→0短闭环通过，取本文§10及[后续计划§9.6](../../blinker-library/docs/DEVICE_V2_USABILITY_FOLLOWUP_EXECUTION_PLAN.md#96-n5-本机数值短验收2026-10-11收口)。命名/编辑/启用、真实ACK/State、退出App后执行、查询、停用/删除均沿原链路。原账号/请求保留，安装归档限定仍记录；软件、限定真机与生产分别记录，不扩复杂功能。

## 1. M1～M5范围与依据

保留现有范围：同账号、同租户及分片的两台普通 WiFi 设备；布尔变化和数值阈值作为条件，一个可写属性固定赋值作为动作。M1～M5为boolean，后续N5有限扩为boolean/uint32；其他目标不开放。创建默认停用，用户明确启用；App退出不停止云端规则。原基线、回差、30秒冷却、容量、权限与未知执行保护不变。

交互参考 [IFTTT 创建说明](https://ifttt.com/docs/applets)：简短标题说明用途，以触发和动作组织配置，隐藏不需要用户填写的技术字段。参考[米家联动使用手册](https://ics-resources.xiaomi.com/ics-resources/articles/60c308fcad904a4ba10aa587.html)：先选择条件，再选择设备动作，手动场景和自动联动分开。这些是交互依据，不是其内部执行架构的证明。

M1～M5不增加多条件、多动作、延时、日历触发、脚本、按钮 Action、数值目标、BLE-only 或网关本地执行。后续N5只开放bool/uint32单Property目标，未改变上述M5实物证据；旧严格App会拒绝数值分支，须匹配Gateway/Broker更新，不宣称旧组合无感兼容或允许降级新规则。设备库、MQTT、BBP/2和规则判定核心保持。

## 2. 用户流程

M1～M5有限产品验收后，N1～N4限定短验收均已收口，N4原环境/账号/3条任务意图保全取[§8.4](../../blinker-library/docs/DEVICE_V2_USABILITY_FOLLOWUP_EXECUTION_PLAN.md#84-n4-本机有限任务展示验收2026-10-10收口)。当前N5用缓存Manifest只提供可写bool/uint32 Property目标，uint32输入没有默认值，零合法，切换目标清旧输入；编辑保留原端点、原ID与精确CAS，恢复始终使用原日志正文，不按当前草稿重组。数值按原值展示、布尔沿N1状态名称，不猜单位或新增显示框架。N1显示元数据按logicalDeviceId＋key/kind/type解析，规则名称另按原合同；自动化冲突仍按目标设备而非属性。不重开M5执行链，不借旧实物证明新数值门禁。

本批匹配Service051与修订App已备份后部署：真实昵称/别名/布尔文案在控制、自动化列表及编辑器复用，重启/离线显示缓存、附近TTL及后台12秒扫描预算短验收通过。异步父标题与确认放弃草稿后的DOM刷新已最小修正并真机复测，最终联合40文件/491项通过；只补Angular通知，不改状态判定或执行链。临时显示恢复，定时、共享/CAS等未覆盖项取[后续计划§6](../../blinker-library/docs/DEVICE_V2_USABILITY_FOLLOWUP_EXECUTION_PLAN.md#6-本机匹配版本短验收2026-10-10)。不扩规则能力或重新执行M5全套。

1. “我 → 自动化”直接进入规则列表；旧 `/scene-manager` 入口重定向到相同页面。
2. 列表展示名称、可理解的条件和动作摘要、启停状态及必要异常。提供新建、详情及明确标注的历史入口，不同时堆叠表单、技术说明和执行记录。
3. 新建按照“名称 → 当设备条件变化时 → 执行设备动作”组织；数值输入保留阈值和有效正回差，不猜测单位或填入适用于所有设备的默认回差。无能力缓存时引导先读取对应设备能力，不自动连接全部设备。
4. 保存得到停用规则，详情中明确启用。编辑现有规则可以修改名称、条件和目标值；本批源与目标端点保持原样，避免扩大端点迁移和能力恢复范围。
5. 编辑已启用规则必须明确确认，沿原 ID 和精确版本提交；不删除重建、不自动绕过版本冲突。编辑后重新建立基线的行为沿原实现，不把保存当立即执行。
6. 详情提供启停、编辑、删除及最近执行结果。删除沿用软退役，不能重新启用，历史不删除；已发命令不能被召回。
7. 保存结果未知时显示“结果待确认”，先核对原请求；恢复仍须明确确认原请求。ID、原版本和原请求正文收进技术详情，但不得隐藏真实未确认状态。

布尔条件使用“从关闭变为开启／从开启变为关闭”，不能改写为持续状态条件；数值条件使用“升至／降至阈值时”，继续解释离开回差区才允许再次触发，不因文案简化改变语义。

## 3. 名称持久化与兼容

公开 HTTP 管理合同增加可选 `name`，与设备协议和条件 policyVersion 无关。显式提交名称须为合法 Unicode 字符串，拒绝控制字符及未配对代理项；去除首尾空白后非空，最多80个 UTF-16代码单元，不做额外 Unicode 归一化。

- 新 UI 提交明确名称；旧规则、旧响应和旧持久意图没有该字段仍可读取。
- 旧规则没有名称时使用条件和动作生成展示标题，不批量回填数据库或把展示标题冒充已保存名称。
- Service 使用原规则表的 nullable `name` 与原始创建元数据 `create_name`，通过迁移050加入；不改 definition/digest/观察事实和命令帧。
- 省略名称的旧编辑保留当前名称。原创建重试核对初始名称，修改重试核对当前名称，版本冲突仍沿原合同。
- 名称与原条件更新同事务提交；App 在持久化新意图前完成校验，未确认的原意图不按新表单或新名称改写。原意图带名称时，确认结果必须同时匹配名称。

只改名仍沿原PUT／CAS增加definitionRevision并重新建立基线，不新增独立改名接口。新App与带名称的Service响应必须匹配升级；旧无名称数据兼容不代表旧APK的严格模型能够读取新命名规则。测试和部署状态必须分开记录。

## 4. 状态与信息分层

| 信息 | 普通页面 | 技术详情 |
| --- | --- | --- |
| 启停 | 已启用、已停用、已删除 | enabled、retiredAtMs |

真实App渲染控件完成同一规则revision1停用命名创建、revision2启用目标50、revision3编辑名称及目标0且保持启用、revision4停用、revision5软删除；原ID/端点/CAS保持。两真实源边沿分别产生目标level=50/0及回调1/2，PG与原ledger均ACK200、序列5/6、各attempt1，新鲜State与真实Manifest一致。第二次在App force-stop且无PID后执行；重启App可按新名查询两条“设备已确认”。停用/删除后超冷却再分别真实源0→1，Broker确认收到新State而无新执行/目标回调；历史仍可读且无启用/编辑入口。不以页面显示替代真实设备或持久ACK。
