### 2. 调查步骤

1. **建立源功能地图**：从 app.routes、app.config、AppComponent 进入，确认设备首页、添加、区域、共享、控制、设置与编辑子路由。
2. **追踪真实依赖**：读取关键文件结构后检查具体实现，包括 DataService、DeviceService、DeviceUiPort、BBP2、共享权限、区域 revision 和设备面板保存。
3. **核对 UI 复用边界**：确认 Ionic、主题、翻译、设备图片、字体，以及 device-template/custom-panel 两条额外构建链。
4. **核对平台能力**：确认移动 BLE 扫描/控制/凭据、WiFiProv、LAN 默认开关、App 前后台和 Network 实现。
5. **并行只读调查**：使用一个文件分析 subagent，核对现有 subapp 模板、真实 Angular 包、宿主 ready/Penpal/WebSocket、安装、打包、登录、存储及生命周期；未委派代码实现。
6. **补充认证方向**：用户明确宿主可以修改后，将方案由“不能假定能共享登录”推进到“改宿主支持统一登录”，并补查设备网关上游鉴权实现。
7. **形成交付物**：撰写调查报告、执行计划和本记录；架构图、业务数据流图、宿主认证时序图均嵌入 Markdown。

### 3. 关键发现的修正记录

| 初步可能误判 | 核对后的结论 |
| --- | --- |
| 五个页面就是迁移范围 | 至少包括其设备设置、面板编辑、邀请/公开控制台、认证和配网依赖；按可达闭环确定 |
| 模板 Angular 21，源 UI 需降级 | iframe 独立运行，可保留源 Angular 22/Ionic；复用外壳契约即可 |
| 页面运行即意味着 BLE/配网支持 | WiFiProv Web 方法明确不可用；需要桌面 transport 与真机验证 |
| localStorage 已满足持久化 | subapp 随机 loopback 端口改变 origin；必须稳定存储 |
| mqtt-debugger 没有 MQTT | Node core 是基础壳，但 UI 有 MQTT over WebSocket；不适合当共享后台服务 |
| resourceLifecycle 已支持全部设备资源 | 当前宿主适配主要是串口；BLE/MQTT 退出需自己实现 |
| 同名用户/token 外形就代表可 SSO | 进一步找到同上游账号服务和 Bearer 转发源码；仍需确认部署与区域 |
| 支持宿主账号就应将整个工具强制登录 | 源端有匿名公开控制台；认证能力、登录门槛和退出清理必须分别处理 |
| 整个 layouter2 都要复制 | 当前动态注册已将旧组件名映射到 LegacyPanelComponent；按真实依赖迁移 |
| 日志/存储展示代表真实接口已完成 | 源端存在演示兜底；记录限制，不用来证明设备联调成功 |
